# Pinecrest Care Coordinator

**Calling the right patients first: a 30-day readmission worklist built end to end on Databricks.**

Pinecrest Health is a fictional three-hospital system. Every record in this repo is synthetic,
generated by [`data_gen/generate.py`](data_gen/generate.py) with a fixed seed. No real patients,
customers or PHI.

---

## The problem, and who owns it

One in seven Pinecrest patients (14.7%) is readmitted within 30 days. Three executives feel
that number differently:

| Executive | Accountable for | What this build changes for them |
|---|---|---|
| **Chief Quality Officer** (sponsor) | The 30-day readmission rate and the CMS HRRP penalty that follows it, reported to the board | A ranked worklist that sends coordinators to the top-risk decile first, where readmissions run 3.34× the average |
| **CFO** | HRRP penalty exposure (up to 3% of Medicare reimbursement) and ~$15K of cost per avoidable readmission | ~$3M a year of avoided cost per point of rate reduction at a 20,000-discharge system (illustrative), plus penalty relief |
| **VP of Care Management** | A fixed team of coordinators who can only call a fraction of each day's discharges | The same team, the same morning, a better first call, with every approved action recorded |

The data shows where the care team can act. Patients discharged without a follow-up visit are
readmitted at **19.2%**, against **11.8%** for those with one booked
([evidence/07](evidence/07_deck_figures.md)). Disposition is fixed at discharge; the follow-up
can still be booked the next morning.

## What the coordinator gets

A Databricks App that, every morning:

1. **Ranks** every recent discharge by predicted 30-day readmission risk (High / Medium / Low).
2. **Explains** a patient's risk in a few lines, grounded in that patient's own coordinator notes.
3. **Recommends** a next action, which the coordinator can edit.
4. **Records** the approved action, with approver and timestamp, in Lakebase.

Real output for patient `PC-01684`, from the app log ([evidence/06](evidence/06_app_execution.md)):

> **Barriers to follow-up:** transportation to a follow-up visit isn't arranged yet (per the
> daughter), and the patient reports that the cost of the inhaler and copays is a barrier.
> **First action:** schedule the follow-up visit within 7 days and book it together with transportation.

## Decisions and trade-offs

- **Gradient boosting, not a deep model.** Six thousand tabular discharges, a need to explain
  scores to clinicians, and a nightly batch: a GBM fits all three and trains in seconds.
- **Batch scoring into a table, not a real-time endpoint.** Discharges arrive once a day and
  coordinators work the list each morning, so a nightly score is enough and keeps cost near zero.
  A serving endpoint is the upgrade path if scoring needs to happen at discharge time.
- **Lakebase synced tables, not app queries against the warehouse.** The app gets ~4 ms reads and
  transactional writes; the cost is sync lag, which is acceptable for a daily score.
- **Read-only synced tables, writable action table.** The app's service principal has `SELECT`
  on the synced tables and write access only to `care_actions`, so the app cannot drift the
  data that Unity Catalog governs.

## What went wrong along the way

- **Governed tags rejected my first values.** The workspace's tag policies only allow approved
  values for `domain` and `data_class`, so I used `clinical` and `amber` rather than creating
  ungoverned tags.
- **The serverless environment had no MLflow.** The training notebook now pins its own
  dependencies, so the run does not depend on what the environment happens to include.
- **A smoke test wrote to a synced table.** As the table owner I was allowed to update a synced
  row, which would silently diverge from Unity Catalog. I restored the row (the one-line repair
  is still in `04_lakebase/setup_lakebase.py` and is a no-op on re-run), removed the test, and
  rely on the app's `SELECT`-only grant instead.
- **The first LLM call failed in the app.** The SDK expects typed chat messages. I fixed it,
  added structured logging for every explanation and approval, and verified the write-back by
  reading it from Lakebase in a separate job.

## What I would build next

- **Row-level security by facility**, extending the column mask so a Valley coordinator only sees
  Valley patients.
- **An inference table for the LLM explanations**, so every prompt and response is governed in
  Unity Catalog alongside the care-action audit trail.
- **Drift-triggered retraining**: a scheduled job that compares the incoming discharge mix with
  the training data and retrains when it shifts, promoting only if the new version beats `@champion`.
